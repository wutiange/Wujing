d:T8ce6,<h2 id="前言">前言</h2>
<p>用 <code>react-native-ble-plx</code> 做指令队列时，我以为自己已经很熟了，结果还是踩了坑。代码最初是 AI 生成的；出问题后排查了很久，根因是：本次任务的等待挂在 <code>write</code> 之后——设备秒回时，全局 <code>monitor</code> 已经把 notify 消费掉，却没有对应的 <code>resolve</code> 接住，业务侧只能等到超时。</p>
<p>前一家公司做蓝牙 App 时，就见过「先下发、再挂本次等待」的写法。当时觉得有隐患，也改过公司代码，但那次只是审查上的直觉，并没有线上故障可复现。</p>
<p>对库还不熟时，可先看官方文档：<a href="https://github.com/dotintent/react-native-ble-plx">react-native-ble-plx</a>。</p>
<p>本文按「现象 → 问题代码 → 根因 → 修复 → 延伸」说明；顺带记一件更值得想的事：逻辑有隐患、线上却没炸时，该不该改、怎么说服别人改。</p>
<h2 id="一业务约定">一、业务约定</h2>
<p>设备端一个服务，两个特征值：</p>
<table>
<thead>
<tr>
<th>方向</th>
<th>特征值</th>
<th>含义</th>
</tr>
</thead>
<tbody>
<tr>
<td>App → 设备</td>
<td>write</td>
<td>下发指令</td>
</tr>
<tr>
<td>设备 → App</td>
<td>notify</td>
<td>回传结果</td>
</tr>
</tbody>
</table>
<p>例如 App 发查询指令后，要在 notify 上拿到设备信息，再结束这次 <code>writeData</code> 的 Promise。</p>
<p>连接成功后，notify 特征上会挂<strong>全局</strong> <code>monitor</code>：一直在听，不是每次发指令才临时订阅。回包到来时，它找到当前任务并调用其 <code>resolve</code>。</p>
<p>这里有两层东西，后面根因会用到：</p>
<table>
<thead>
<tr>
<th>层级</th>
<th>作用</th>
</tr>
</thead>
<tbody>
<tr>
<td>全局 <code>monitor</code></td>
<td>接收 BLE notify</td>
</tr>
<tr>
<td>本次任务的等待（<code>waitForTask</code> / <code>task.resolve</code>）</td>
<td>把这次回包交接给业务 Promise</td>
</tr>
</tbody>
</table>
<p>监听负责「收到」；等待负责「交给这次发送的调用方」。两层都就绪，一次指令才算完整。</p>
<h2 id="二问题现象">二、问题现象</h2>
<table>
<thead>
<tr>
<th>维度</th>
<th>情况</th>
</tr>
</thead>
<tbody>
<tr>
<td>触发场景</td>
<td>高频下发 + 设备端几乎秒回</td>
</tr>
<tr>
<td>表面表现</td>
<td>跑一段时间后卡住，等到超时长才失败</td>
</tr>
<tr>
<td>误导点</td>
<td>前面多次成功，容易怀疑设备端</td>
</tr>
<tr>
<td>真实结果</td>
<td>notify 已被全局 monitor 消费，本次等待尚未挂上，没有对应的 <code>resolve</code> 接住</td>
</tr>
</tbody>
</table>

<h2 id="四根因分析">四、根因分析</h2>
<h3 id="1-排查过程">1. 排查过程</h3>
<p>一开始更怀疑设备端——第一次写设备侧逻辑，成功过几次也不敢自信。但连接未断、用其它 App 测也正常时，应按理把焦点转回 App。</p>
<p>卡住最终走超时 <code>reject</code>，说明业务侧的 <code>resolve</code> 从未被等到。日志和设备侧都表明有回包，全局 <code>monitor</code> 也一直开着。继续顺着代码模拟执行，问题收束到 <code>_send</code> 里 <strong><code>writeWithResponse</code> 与 <code>waitForTask</code> 的先后</strong>：等待挂在 write 返回之后。</p>
<h3 id="2-机制提前消费没有对应的等待者">2. 机制：提前消费，没有对应的等待者</h3>
<p>系统里其实一直有人在「听」——全局 <code>monitor</code>。失败不是因为没收到 BLE 数据，而是收到之后的交接断了。</p>
<p>具体链路：</p>
<ol>
<li><code>currentTask = task</code> 已设置，<code>monitor</code> 回调能找到「当前任务」这个对象。</li>
<li>但 <code>waitForTask</code> 还没执行：用来把回包交给业务 Promise、并结束本次 <code>await</code> 的那层包装尚未挂上。</li>
<li>设备秒回 → <code>monitor</code> 触发 → 调用当时的 <code>task.resolve</code>（仍是入队时的原始 resolve，或等价地：没有与 <code>waitForTask</code> 绑在一起的那套逻辑）。</li>
<li>这一包 notify 已经被回调消费掉了。</li>
<li>随后 <code>writeWithResponse</code> 返回，才执行 <code>waitForTask</code>，开始空等；只能等到超时。</li>
</ol>
<p>所以根因应表述为：</p>
<blockquote>
<p><strong>回包被全局监听提前消费了，但当时没有对应的等待者把这次消费交接成业务上的完成。</strong></p>
</blockquote>
<p>两层不同步时，表现就是「有监听、有回包、业务却超时」。</p>
<h3 id="3-时序">3. 时序</h3>
<pre class="mermaid-source"><code class="language-mermaid">sequenceDiagram
  participant App
  participant W as write 特征
  participant Dev as 设备
  participant M as 全局 monitor

  App-&gt;&gt;App: currentTask = task
  Note over M: monitor 早已在听
  App-&gt;&gt;W: writeWithResponse(cmd)
  W-&gt;&gt;Dev: 下发
  Dev-&gt;&gt;M: 秒回 notify
  M-&gt;&gt;M: 消费回包，但 waitForTask 尚未挂上
  Note over M: 提前消费，没有对应的 resolve 交接
  W--&gt;&gt;App: write 返回
  App-&gt;&gt;App: 此时才 waitForTask(task)
  Note over App: 只能等到超时 reject</code></pre>
<p>设备慢时，回包常落在 <code>waitForTask</code> 之后，问题被掩盖；秒回 + 高频下发时更容易打中。前面多次成功，只说明还有别的时序因素，不否定这个隐患。</p>
<p>另外：若 <code>waitForTask</code> 在 <code>write</code> <strong>之前</strong>就已挂好，即便 notify 打在 <code>writeWithResponse</code> 尚未返回期间，<code>monitor</code> 也能把结果交给本次等待，后面的 <code>await waiting</code> 会立刻结束。因此关键不是「两个 <code>await</code> 谁先写在源码里」，而是 <strong>等待是否在下发前就已经就绪</strong>。</p>
